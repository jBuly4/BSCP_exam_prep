# BSCP Exam: Алгоритм действий от открытия стенда до эксплуатации
This guide is made by [Angelionix](https://github.com/Angelionix) 

> **Цель**: систематический триаж экзаменационного стенда за 30-40 минут на уязвимость.
> **Инструмент**: Burp Suite Pro + браузер через прокси.
> **Формат**: пошаговый алгоритм с пояснениями в скобках.

---

## Фаза 0: Подготовка (0-5 мин)

### 0.1 Запуск Burp Suite Pro

Запускаю Burp Suite Pro, подключаю браузер через прокси, убеждаюсь что трафик идёт через Burp.
*(Без Burp экзамен не сдать — весь анализ идёт через Proxy History. Если трафик не видно — экзамен не начнёшь.)*

### 0.2 Настройка Burp

В Burp: Project Options → Connections → ставлю галочку «Follow redirects», Intercept **off**.
*(Перехват включаю только точечно, когда нужно модифицировать конкретный запрос. Иначе будет спам и потеря времени.)*

### 0.3 Первичный обход

Открываю экзаменационный URL в браузере, логинюсь если есть учётка, прохожу весь функционал как нормальный пользователь.
*(Понимаю что делает приложение: какие роли, какие действия, какие данные. Это контекст для всего дальнейшего анализа.)*

## Фаза 1: Пассивная разведка (5-15 мин) — самая важная фаза

### 1.1 Максимальный обход

Ползаю по приложению: кликаю каждую ссылку, заполняю каждую форму, загружаю файлы, выхожу из аккаунта, регаюсь заново.
*(Каждый запрос идёт в Proxy History — это база данных для анализа. Чем больше запросов, тем больше зацепок. Не жалей времени на этот шаг — он определяет всё.)*

### 1.2 Маркировка Proxy History

Параллельно просматриваю Proxy History и помечаю интересные запросы по маркерам:

| Маркер в ответе/запросе | → Класс атаки |
|---|---|
| `X-Cache`, `Age`, `X-Cache-Status`, `Via`, `CF-Cache-Status` | Web Cache Deception |
| `Access-Control-Allow-Origin: *` или echo моего Origin | CORS |
| `Set-Cookie` без `Secure`/`HttpOnly`/`SameSite` | Cookie-атаки |
| Параметры `?file=`, `?path=`, `?template=`, `?lang=`, `?page=` | Path Traversal / SSTI / LFI |
| Параметры `?url=`, `?redirect=`, `?next=`, `?return=` | SSRF / Open Redirect |
| Параметры `?id=`, `?user=`, `?uid=` | IDOR |
| Формы с текстовым вводом, слабый/отсутствует CSP | XSS |
| JSON/XML тела запросов | Deserialization / Injection |
| WebSocket соединения | WS-атаки |
| Эндпоинты `/api/` | API Testing |
| `debug=`, `admin=`, `internal=` | Info Disclosure |

*(Один запрос может дать несколько маркеров — отмечаю все. Маркер ≠ уязвимость, но маркер = направление для проверки.)*

### 1.3 Анализ Target Site Map

Смотрю Target Site Map (дерево URL) — ищу:
- Скрытые эндпоинты (не видны в UI, но в карте есть)
- Директории `/admin`, `/debug`, `/console`, `/backup`, `/.env`
- Разные контекст-пути для одного функционала

*(Site Map показывает всё что Burp нашёл автоматически — часто там есть то, что ты не кликал руками. Это бесплатная разведка.)*

### 1.4 Анализ HTTP-заголовков

Проверяю HTTP-заголовки ответов:

| Заголовок | Что даёт |
|---|---|
| `Server: Apache/2.4.49` | Path Traversal (CVE-2021-41773) |
| `Server: nginx/1.16` | Возможен HTTP Smuggling |
| `X-Powered-By: PHP` / `Express` / `ASP.NET` | Подсказывает стек технологий |
| Слабый/отсутствует CSP | XSS легче эксплуатировать |
| Строгий CSP | Возможно Cache Deception вместо XSS |
| `X-Forwarded-For` обрабатывается | SSRF / Header injection |
| `X-Original-URL` обрабатывается | Access Control bypass |

## Фаза 2: Активный триаж — решающее дерево (15-25 мин)

Систематически проверяю индикаторы из Фазы 1. Порядок — от быстрых побед к сложным.

### 2A. Web Cache Deception

**Условие проверки** — есть хотя бы ОДИН маркер:
- Ответ содержит `X-Cache`, `Age`, `CF-Cache-Status`, `Via`
- CDN-домен (Cloudflare, Akamai, Fastly) — виден по заголовкам или IP
- Статические ассеты кэшируются (`Age > 0`)

**Действия:**

```
1. Беру запрос к /my-account (авторизованный) → Send to Repeater
2. Добавляю расширение к URL: /my-account/stylesheet.css
3. Если ответ 200 с моими данными И X-Cache: HIT → Cache Deception ПОДТВЕРЖДЕНА
4. Если HIT но пустой → пробую сепараторы: /my-account%0astyle.css, /my-account/..%2fstylesheet.css
5. Если всё MISS → откладываю, возвращаюсь если не найду ничего лучше
```

*(Cache Deception — одна из самых быстрых побед: 5-10 мин на эксплуатацию если кэш есть. Проверяю в первую очередь при наличии маркеров.)*

### 2B. Host Header Attack

**Условие проверки:**
- Виртуальный хостинг (разные сайты на одном IP)
- Ссылки в ответе содержат Host-заголовок (динамические)
- Функционал password-reset содержит ссылку
- `X-Forwarded-Host` обрабатывается сервером

**Действия:**

```
1. Отправляю запрос в Repeater
2. Меняю Host: на свой Burp Collaborator URL
3. Если Collaborator получил DNS/HTTP callback → Host Header Injection ПОДТВЕРЖДЕНА
4. Если пароль-ресет ссылка содержит мой Collaborator → CRITICAL, эксплуатирую немедленно
5. Если X-Forwarded-Host работает → использую его вместо Host
```

*(Host Header — часто связан с password reset poisoning. Это быстрая победа если Collaborator колбэкнит.)*

### 2C. HTTP Request Smuggling

**Условие проверки:**
- Перед приложением стоит прокси/CDN/LB (видно по `Via`, `X-Forwarded-*`, разным `Server` заголовкам)
- Фронтенд и бэкенд по-разному обрабатывают `Transfer-Encoding` / `Content-Length`
- Используется HTTP/1.1 (HTTP/2 неуязвим к классическому smuggling)

**Действия:**

```
1. POST-запрос → Send to Repeater
2. Добавляю Transfer-Encoding: chunked + Content-Length
3. Тело: 0\r\n\r\nG (smuggled prefix)
4. Если таймаут / ошибка / 500 → возможен smuggling
5. Подтверждаю: два запроса подряд, второй содержит ответ первого
6. Определяю тип: CL-TE vs TE-CL (по поведению)
7. Если подтвердился → перехожу к эксплуатации (smuggle запрос к /admin)
```

*(Smuggling сложнее, но если есть два сервера — почти гарантированная уязвимость. Занимает 20-30 мин. Не начинай с этого если есть более быстрые маркеры.)*

### 2D. CORS

**Условие проверки:**
- Ответ содержит `Access-Control-Allow-Origin` с моим Origin
- Или `Access-Control-Allow-Credentials: true`
- Или Origin отражается в заголовках

**Действия:**

```
1. Отправляю запрос с Origin: https://evil.com
2. Если ACAO: https://evil.com + ACAC: true → CRITICAL
3. Если ACAO: null → эксплуатирую через iframe sandbox
4. Если ACAO: поддомен.evil.com → нужен контроль поддомена
5. Если ACAO без credentials → ограниченная ценность, но может комбинироваться
```

*(CORS — быстрая победа если Origin отражается. Проверяю сразу после Cache Deception.)*

### 2E. SQL Injection

**Условие проверки:**
- Параметры с числовыми ID, поиск, формы логина
- JSON/XML с внедряемыми полями
- Ошибки БД в ответах (MySQL, PostgreSQL, Oracle, MSSQL)

**Действия:**

```
1. Добавляю ' к каждому параметру → 500 / error → маркер
2. Добавляю ' OR 1=1-- → изменившийся ответ → маркер
3. Если ошибок нет но поведение разное → Blind SQLi
4. Если UNION SELECT работает → UNION-based (самый удобный)
5. Если SLEEP(10) / WAITFOR DELAY → Time-based blind (дольше, но работает)
```

*(SQLi — классика, проверяю всегда. Если есть маркер — почти гарантированно эксплуатируется.)*

### 2F. XSS

**Условие проверки:**
- Текстовый ввод отражается в ответе без эскейпинга
- CSP слабый или отсутствует
- Загружаемые файлы могут содержать HTML/JS

**Действия:**

```
1. Ввожу уникальную строку (xss7test) в каждое поле
2. Поиск в ответе: отражается ли? В каком контексте?
   - HTML tag context: <script>alert(1)</script>
   - Attribute context: " autofocus onfocus=alert(1) "
   - JS context: ';alert(1);//
3. Если отражается → подбираю payload по контексту
4. Reflected → эксплуатирую сразу; Stored → ищу где хранится и кто видит
```

*(XSS — частая уязвимость на экзамене. Если ввод отражается — это почти всегда XSS.)*

## Фаза 3: Приоритизация и углубление (25-35 мин)

### 3.1 Ранжирование по скорости победы

| Приоритет | Уязвимость | Время | Почему быстро |
|---|---|---|---|
| 🥇 | IDOR / Access Control | 2-5 мин | Меняю ID → готово |
| 🥇 | Info Disclosure | 3-5 мин | URL-манипуляция → данные |
| 🥈 | Cache Deception | 5-10 мин | Если кэш есть — быстро |
| 🥈 | CORS | 5-10 мин | Если Origin отражается |
| 🥈 | Host Header | 5-10 мин | Если Collaborator колбэкнит |
| 🥉 | XSS | 10-15 мин | Если отражается |
| 🥉 | SQLi | 10-20 мин | Зависит от типа |
| 🥉 | SSTI | 10-20 мин | Если шаблон найден |
| 4️⃣ | Smuggling | 20-30 мин | Требует терпения |
| 4️⃣ | Deserialization | 15-25 мин | Если сериализация есть |
| 4️⃣ | NoSQL Injection | 10-20 мин | Если MongoDB/NoSQL |

### 3.2 Стратегия эксплуатации

Беру самый быстрый маркер → эксплуатирую полностью → сдаю → перехожу к следующему.
*(Никогда не начинаю со сложных если есть лёгкие. Экзамен — про скорость, не про элегантность. Одна сданная уязвимость лучше чем три начатых.)*

### 3.3 Углубление если быстрых побед нет

- Запускаю Burp Scanner (Active Scan на целевой домен)
- Пробую Content Discovery (Burp → Engagement Tools → Find content)
- Brute-force директорий через Intruder
- Проверяю каждую форму на все классы уязвимостей

## Фаза 4: Если застрял — чеклист (что я мог пропустить?)

### 4.1 Нет никаких маркеров?

- Пробую `/admin`, `/administrator`, `/staff`, `/management`
- Меняю роль в cookie/JWT (`user` → `admin`, `roleid: 0` → `roleid: 1`)
- Меняю метод GET↔POST↔PUT↔DELETE
- Добавляю `X-Original-URL: /admin`, `X-Rewrite-URL: /admin`
- Пробую `X-Forwarded-For: 127.0.0.1`, `X-Forwarded-Proto: https`

### 4.2 Есть маркер но не эксплуатируется?

| Маркер | Углубление |
|---|---|
| XSS не работает | Проверяю CSP, пробую обход: event handlers, svg, body onload, mutation XSS |
| SQLi не работает | Пробую другие контексты: Cookie, Header, JSON key, XML element |
| Cache MISS | Пробую другие расширения, пути, сепараторы (`%0a`, `%23`, `..%2f`) |
| Smuggling не подтверждается | Пробую CL-CL, H2.CL, разные значения TE |
| SSRF не работает | Пробую разные протоколы: `gopher://`, `file://`, `dict://`, IPv6 `[::1]` |
| SSTI не определяется | Пробую `{{7*7}}`, `${7*7}`, `<%= 7*7 %>`, `{7*7}`, `#{7*7}` |

### 4.3 Совсем ничего?

Беру перерыв 2 мин, смотрю Proxy History свежим взглядом.
*(Часто ответ прямо перед глазами, но мозг «замылился». Новая пара глаз — это не метафора, а нейробиология: префронтальная кора перезагружается.)*

## Тайм-менеджмент: железные правила

| Время | Действие |
|---|---|
| 0-5 мин | Настройка Burp + первичный обход |
| 5-15 мин | Пассивный анализ (Proxy History + Site Map) |
| 15-30 мин | Активный триаж по маркерам |
| 30-40 мин | Эксплуатация первой уязвимости |
| >15 мин на эксплуатацию без результата | **ПЕРЕКЛЮЧАЮСЬ** на другой класс |
| >40 мин на одну уязвимость | **ОБЯЗАТЕЛЬНО переключаюсь** |

**Главное правило**: на экзамене 6 уязвимостей за 4 часа. Нет времени «продавливать» одну. Если за 15 минут не получаю прогресс — меняю направление.

## Быстрая шпаргалка: маркер → действие

```
Вижу X-Cache / Age                    → Проверяю Cache Deception
Вижу ACAO с моим Origin               → Проверяю CORS
Вижу два Server-заголовка (фронт+бэк) → Проверяю HTTP Smuggling
Вижу Host в теле ответа               → Проверяю Host Header
Вижу ?id= / ?user=                    → Проверяю IDOR
Вижу ?url= / ?redirect=               → Проверяю SSRF
Вижу ?file= / ?path= / ?template=     → Проверяю Path Traversal / SSTI
Вижу отражение ввода без эскейпинга   → Проверяю XSS
Вижу ошибку БД                        → Проверяю SQLi
Вижу JSON/XML с сериализацией         → Проверяю Deserialization
Ничего не вижу                        → Углубляюсь: Scanner, Content Discovery, Access Control
```
